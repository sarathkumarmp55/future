# future app

- Site: `future.com` (bench at `/home/user/frappe-benchA15`, apps install via `sites/apps.txt`; future not yet in apps.txt, list via `bench --site future.com list-apps` shows it installed).
- Wire Program doctype JS via `doctype_js` in `future/hooks.py` -> `public/js/program.js`.
- Program doctype custom fields: child table `custom_fees_details` (Table -> "Fees Details") with `component`+`amount`, and Currency `custom_total_amount`. Sum of child `amount` is written to `custom_total_amount` from `public/js/program.js`.
- Child table removal event name is `<child_field>_remove`, i.e. `custom_fees_details_remove`.
- `Payment Approval Log.on_submit` builds the Sales Invoice programmatically (both `from_opportunity` and `from_student_service` paths). Item tax templates (e.g. Orientation Fee -> "18 - F" @ 18%) are NOT auto-applied on programmatic `insert()`; must call `invoice.set_missing_values()` + `invoice.append_taxes_from_item_tax_template()` (after setting `invoice.company`) to populate `item_tax_template`/`item_tax_rate` and the `taxes` table. `add_taxes_from_item_tax_template` is enabled in Accounts Settings, so the JS-side behavior is mirrored this way server-side.
- Fee `received_amount` is treated as GST-INCLUSIVE. Mark the appended tax rows `tax.included_in_print_rate = 1` so ERPNext back-calculates net + tax from the gross rate (avoids the 1-paise drift of manually dividing `received_amount / 1.18`, which produced grand_total=4000.01 vs outstanding=4000.00 and the "Allocated Amount cannot be greater than outstanding amount" error).
- The Payment Entry must allocate `invoice.outstanding_amount` (not `invoice.grand_total`, which can differ by rounding) and use `invoice.grand_total` for `paid_amount`/`received_amount` so the invoice fully settles.
- Lead list dashboard lives in `public/js/lead_list.js` (wired via `doctype_list_js`), calling `future.api.get_dashboard_data`. Payment Approval Log has a separate dashboard in `public/js/payment_approval_log_list.js` calling `future.api.get_payment_approval_dashboard_data` (green filter bar, amount summary cards for fees/hostel/vehicle/total_bill_amount, status counters for total/pending/approved/rejected/from_opportunity/from_student_service, Request Source donut, Payment Status bar).
- `Payment Approval Log.total_bill_amount` = sum of `fees_received_amount` + `hostel_received_amount` + `vehicle_received_amount`. It must be set explicitly in both creation paths (`future/api.py::create_payment_approval_log` and `student_service.py::on_submit`); the form JS only computes it on `refresh`.
- `Discount.program` is a child table (Table -> "Multiselect Program", child field `program` Link->Program), not a single Link. So link queries on `Opportunity.custom_discount_id` and `Student Service.new_discount_id` can NOT use a plain `program:` filter; they use `query: "future.api_2.get_discounts_for_program"` (whitelisted search method in `future/api_2.py` that matches child-table `parent` rows).
- Custom Sales Invoice print format "Fee Receipt" lives in `future/future/print_format/fee_receipt/fee_receipt.json` (A4, Jinja, standard). It expects the company logo at `/files/future-logo.png`; header uses the Future powered by Gokulam address from the user's screenshots.
- Lead `custom_lead_manager_name` (role "Lead Manager") and `custom_team_leader` (role "Team Lead") are Links -> User whose options are restricted to users present in `Team Heirarchy` with that role, via `query: "future.api.get_team_heirarchy_users"` (filters `{role: ...}`) set in `public/js/lead.js::setup`. The method is whitelisted, `@frappe.validate_and_sanitize_search_inputs`, joins `tabTeam Heirarchy` + `tabUser`, filters `enabled = 1`, and treats an empty/None `role` as "no role filter". Plain `link_filters` cannot do this because the filter lives on another doctype, not on User.
- Lead "New Task"/"New Event" popup is `frappe.views.InteractionComposer` (frappe core, `frappe/public/js/frappe/views/interaction.js`, shipped in `list.bundle.js`) instantiated from `erpnext/public/js/utils/crm_activities.js::create_task`. It is patched (never edited) from `future/public/js/lead.js::patch_interaction_composer_role_field` (idempotent, also re-called from `refresh`): adds a Select `custom_role` ("Team Lead" / "Lead Manager" / "Lead User", `reqd: 1`) right after `assigned_to`, blocks `create_action` with `frappe.msgprint` when no role is picked (the composer calls `dialog.get_values(true)`, so core `reqd` never blocks), writes the picked role into `ToDo.custom_lead_role` (custom Data field, `ToDo-custom_lead_role`) by shimming `frappe.call` only around `create_interaction` for the `frappe.client.insert` ToDo doc, sets `dialog.fields_dict.assigned_to.get_query` to `future.api.get_team_heirarchy_users` filtered by the picked role (only for Team Lead / Lead Manager; Lead User is not a Team Heirarchy role so it lists all users), clears `assigned_to` on role change, and strips `custom_role` in the patched `get_values` so `frappe.client.insert` never receives the unknown field.
- `Team Lead Wise Report` = Script Report `future/future/report/team_lead_wise_report/` (ref_doctype ToDo, roles Sales User/Sales Manager/System Manager). JS filters: `team_lead` (Link User, default `frappe.session.user`, validated against `Team Heirarchy` role "Team Lead" via `future.api.is_team_lead`), `lead_users` (MultiSelectList fed by `future.api.get_team_lead_users(team_lead)` = active rows of the team lead's `team_heirarchy_table` child table, returned as `{value,label}` for `df.get_data`), `from_date`/`to_date` (default today), `today` (read-only, default today). Python groups per Lead User on `tabToDo.allocated_to`: `overdue` = status Open AND `ToDo.date < today` (independent of from/to), `open`/`closed` = status within `from_date..to_date`; returns a `report_summary` of the three totals. Non-Team-Lead `team_lead` raises ValidationError server-side and msgprints client-side, unless the session user is a Lead Manager (`future.api.is_lead_manager`); for Lead Managers `onload` unlocks the `team_lead` filter (`df.read_only = 0; control.refresh()`) while it stays read-only for everyone else. Adding a report needs `bench --site future.com migrate` to import the Report record.
- `Lead Userwise Report` = Script Report `future/future/report/lead_userwise_report/` (ref_doctype ToDo). JS filters: `user` (Link User, default `frappe.session.user`, read-only), `from_date`/`to_date` (default today). Python returns a single row for `tabToDo.allocated_to = user`: `overdue` = status Open AND `ToDo.date < nowdate()`, `open`/`closed` = status within `from_date..to_date`; plus report_summary.
- `Lead Manager Wise Report` = Script Report `future/future/report/lead_manager_wise_report/` (ref_doctype ToDo), same shape as Team Lead Wise Report but filter `lead_manager` validated with `future.api.is_lead_manager` and the Lead User options come from `future.api.get_team_lead_users(team_lead, role="Lead Manager")` (the helper takes an optional `role`, default "Team Lead", so the Team Lead report is unaffected).
- `Total Count Lead Manager Wise Report` = Script Report `future/future/report/total_count_lead_manager_wise_report/` (ref_doctype ToDo). JS filters: `user` (Link User, default `frappe.session.user`), `from_date`/`to_date` (default today; currently NOT applied to the SQL). Python returns NO columns/rows — only a `report_summary` (Overdue/Open/Closed) counting every `tabToDo` with `allocated_to = user AND custom_lead_role = 'Lead Manager'`: `open`/`closed` are all Open/Closed todos regardless of date, `overdue` = Open AND `date < nowdate()`. JS `onload` overrides the report instance's `toggle_nothing_to_show` to a no-op so the summary-only report shows no "Nothing to show" message.
- Lead list bulk "Assign To" popup (`frappe.ui.form.AssignToDialog` created from `frappe/public/js/frappe/list/bulk_operations.js::assign` with `method: "frappe.desk.form.assign_to.add_multiple"`, `bulk_assign: true`) is patched in `public/js/lead_list.js::patch_assign_to_dialog_role_field`: adds the same Select `custom_role` (Team Lead / Lead Manager / Lead User, `reqd: 1`, so the dialog's own `get_values()` blocks submit) right after `assign_to`, and after a successful assignment calls `future.api.set_lead_assignment_role(doctype, names, allocated_to, role)` with the FIRST user of the `assign_to` array — that method sets `ToDo.custom_lead_role` on the ToDos of those docs for that user and, for `doctype == "Lead"`, writes `allocated_to` into `custom_lead_manager_name` / `custom_team_leader` / `custom_lead_user` depending on the role. The call is hooked by shimming `frappe.call` around the dialog's primary action (restored in `finally`).
- `App Access Approval Log` is a Single doctype whose `refresh` repopulates the child table `table_czqr` (options "App Access") with every Student where `custom_app_access_provided = 0`. Its child-button field `app_access_provide` (Button in child doctype "App Access", fired as `frappe.ui.form.on("App Access", { app_access_provide(frm, cdt, cdn) })`) calls `future.api.provide_app_access` (whitelisted in `future/api.py`, along with `get_students_without_app_access` and `provide_app_access_bulk`) which sets `custom_app_access_provided = 1` and `custom_app_access_transaction_id`; the JS then removes that grid row. Both single and bulk ("Provide Access to Selected" custom button, using `grid.get_selected_children()`) flows first open a `frappe.ui.Dialog` prompting for one Access ID (`custom_app_access_transaction_id`); bulk applies that single ID to all selected students then reloads the table. `custom_app_access_transaction_id` (Data) lives in `future/future/custom/student.json` (`sync_on_migrate: 1`, synced via `bench --site future.com migrate`).
- Lead/Opportunity privacy lives in `future/permissions/visibility.py` (hooks `permission_query_conditions` + `has_permission`). Admin / System Manager / Sales Manager see all; Lead Manager sees own + their Team Leads + those leads' users; Team Lead sees own + active team users; everyone else only leads in their `_assign`. A creator loses sight of a lead once it is assigned to someone else. `_assign` is matched with quotes (`%"user"%`) so a@x.com never matches aa@x.com. A `has_permission` hook must return True explicitly (frappe treats None as deny).
- `set_lead_assignment_role` is a hand-over: open ToDos of the same `custom_lead_role` held by other users are cancelled via `assign_to._remove`, which also drops them from `_assign`.
- Lead Dashboard = desk Page `lead-dashboard` (`future/future/page/lead_dashboard/`), data from `lead_dashboard.get_data`, scoped by visibility; the Team performance table is returned only for Team Lead / Lead Manager / managers.
- Desk: `scripts/gen_desk.py` (SPEC is the source of truth) generates Sidebars `Leads` + `Payments`, Dock `future`, Desktop Icon. The site runs in Apps mode, so the tile comes from `add_to_apps_screen` (route `/desk/leads`); the Desktop Icon file only imports in icon-grid mode. Users with module `future` blocked do not get the rail.
- ERPNext 16 replaced `Lead.source` with `Lead.utm_source` (Link UTM Source). Patch `copy_lead_source_to_utm_source` copies the leftover column; queries use `utm_source`.
- Lead hand-over: `future/lead_management.py` is the single path (`hand_over_lead`). Lead Handover (submittable, LHO-) logs moves; Hand Over / Distribute list actions (`public/js/lead_handover_list.js`) and the Lead form button (`public/js/lead_handover_form.js`) call `quick_handover`. Previous holder's open ToDos move to the new person (dated follow-ups keep dates), open Opportunities from the lead follow, a comment is added; cancelling hands back. Only heads (Team Heirarchy) within their teams, or Sales/System Managers, may move leads.
- ToDo `validate` hook `validate_todo_assignment` enforces the same on every Lead/Opportunity assignment path (Assign To sidebar, bulk assign, New Task): salespeople only self or their own heads (`heads_of`). Assignment Rules and imports are exempt.
- Contact / Address linked to a Lead are private too (`contact_*` / `address_*` hooks in visibility.py); ERPNext creates a Contact for every Lead, which otherwise exposed every lead's phone number.
- Auto-assign: Team Heirarchy (Team Lead) has `auto_assign`, `assign_method` (Fewest Open Leads / Round Robin), `max_open_leads`. `maybe_auto_assign` runs when a lead is handed to a Team Lead or saved with a new `custom_team_leader`, and only if no salesperson holds it.
- First-call SLA: `Lead.custom_assigned_on` starts when a salesperson gets the lead (ToDo after_insert `on_todo_insert`, or `hand_over_lead`); the salesperson's own follow-up tasks do not restart it. Hourly `check_first_call_sla` alerts holder + heads once per assignment (`custom_sla_alerted_on`). Daily `send_daily_digest` to heads (bell, optional email). Limits live in the single `Lead Settings`.
- Hand-over requests: a salesperson saving a Lead Handover makes it a request (`request_status` Requested) for leads they hold; heads are notified, approve by submitting, or `reject_request`. Lead Handover visibility = owner / requested_by / handed_over_by within the viewer's visible users.
- Patch `unblock_future_module_for_sales_users` removes the `future` Block Module row for Sales User / Sales Manager users.
